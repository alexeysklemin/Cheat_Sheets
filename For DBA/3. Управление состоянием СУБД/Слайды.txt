Рассматриваемые настройки могут пригодиться при «Подготовка базы к "Большой Интеграции"».

Представьте: к вам прилетают данные из другой системы (например, 1С или SAP). Нужно за ночь залить 50 ГБ данных, построить по ним индексы и сделать так, чтобы утром база летала.
Вот как выглядит этот единый сценарий шаг за шагом:

Шаг 1. Подготовка к загрузке (Уровень 🟢 SIGHUP)
Проблема: Стандартных 4 МБ памяти на сортировку (work_mem) мало. При загрузке CSV-файлов PostgreSQL будет постоянно писать временные файлы на диск, и загрузка займет 10 часов вместо 30 минут.
Действие: Мы временно увеличиваем память для операций сортировки и хеширования.

ALTER SYSTEM SET work_mem = '512MB';
SELECT pg_reload_conf(); -- Применяем мгновенно, не останавливая базу!

Шаг 2. Пост-обработка и индексация (Уровень 🟡 User/Backend)
Проблема: Данные загружены, но теперь нужно построить индексы для быстрого поиска. Операция CREATE INDEX очень прожорлива. Если мы оставим work_mem большим для всех, обычные пользователи могут уронить сервер утром. Но нам нужно много памяти только сейчас и только для админа.
Действие: Мы задаем специальный лимит памяти для обслуживания только для роли postgres.

-- Это изменение подхватится при следующем входе или через SET
ALTER ROLE postgres SET maintenance_work_mem = '4GB'; 
-- Или прямо в сессии:
SET maintenance_work_mem = '4GB';

Результат: Админ строит индексы молниеносно, используя 4 ГБ RAM, пока остальные пользователи продолжают работать со своими скромными настройками. Безопасно и эффективно.

Шаг 3. Финальный тюнинг под новую нагрузку (Уровень 🔴 Postmaster Restart)
Проблема: База выросла. Данных стало в 2 раза больше. Старого кэша в 128 МБ (shared_buffers) катастрофически не хватает. Утром пользователи начнут жаловаться на тормоза, если мы не выделим базе больше общей памяти.
Действие: Мы меняем фундаментальный параметр — размер разделяемого буфера.

ALTER SYSTEM SET shared_buffers = '8GB';
-- Внимание! Это изменение НЕ применится через reload.
-- Требуется полная перезагрузка сервера.
sudo systemctl restart postgresql-custom

Результат: Сервер перезапускается, выделяет 8 ГБ под общий кэш. Утром база «греет» данные в памяти, и все отчеты пользователей летают.
